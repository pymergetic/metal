# Bootstrap, self-hosting, and the quorum

How the system comes into existence, how it takes over its own reproduction, and what stays
outside forever. The predecessor plan (`09-PLAN.md`) built toward a single contained core; this
doc replaces that arc with a two-lane structure: an **external toolchain** that starts as the
authority and ends as an oracle and quorum member, and an **in-artifact core** ported inward one
fixed point at a time.

## Germline and soma

Git is the germline; the lineage is the soma.

- The **repo** never evolves in place. It is fetched fresh, reviewed by humans, and every clone
  is an unmutated copy. It holds the defining level: the intrinsics, the cell header, the
  format version, the op kinds, the face ops, the channel registry.
- A **lineage** starts from a seed minted by the external tool at a repo commit and evolves
  through the plasmid loop (`07`): journaled deltas, acceptance-gated generations. It holds the
  object level: program content expressible within existing kinds — functions, types, knobs,
  objects.

A lineage may rewrite its own object level freely; that is the invention. A lineage that
silently changed its *defining level* would be a program whose definition of correctness
drifted out from under it. The membrane is already in the structures: records are checked
against the declared format version, so a delta touching defining-level material is refused
in-lineage and must re-enter through git — bump format version, mint fresh seed.

Lineages are disposable by design. A drifted or untrusted lineage is abandoned and re-derived
from seed + journal; the germline is never hand-repaired.

## Lineage reproducibility — the certification invariant

Every accepted activation is a journaled delta bound to a base state id and base generations
(`07`). Deltas name ids, never bytes; ids are stable; the writer is deterministic; generations
are content-derived. Therefore:

> A lineage is a pure function of `(seed commit, journal)`. Replay both on a fresh machine
> and you must get the running artifact byte-for-byte — or the lineage is not what it claims.

This turns the external build into a measuring stick: `git fetch && build && rxf replay
--journal <j>`, byte-compare against the running generation. A match certifies the lineage; a
mismatch *locates* the divergence — an unjournaled change, writer nondeterminism, or a change
that bypassed the journal. Enforcement posture (decided): **audit at re-anchor time, prove in
CI** — the in-artifact acceptance gate stays self-contained and does not depend on the external
tool's availability; the git fetch is the checkpoint where the audit runs.

Writer determinism rules that make this true (checked in CI, not by convention):

- no set-iteration order feeds bytes — sort before emit; a `PYTHONHASHSEED` change must not
  change output, and the corpus proves it (build the seed twice under different seeds, diff
  digests) — which is why the sort rule is checked, not assumed;
- no pointer-derived values, no time, no randomness — state ids are digests minted by the
  checker, never UUIDs;
- little-endian canonical form; a big-endian host is a named refusal, never a misread.

## The external toolchain

Pure Python, stdlib-only for the core — `hashlib`, `mmap`, `struct`, `dataclasses`, nothing
else. One `py3-none-any` wheel covers every platform and Python version, no compiler, no
toolchain; channels are extras (`rxf[fuse]`, `rxf[http]`, `rxf[ftp]`), so the certification
path never installs one. The wheel is the IDE-phase "single binary": `pip install rxf` gives
the whole tool on any host.

```
rxf/schema.py      the axioms: every primitive's canonical little-endian layout, one table
rxf/ (core)        reader/checker, viewgen, writer/formatter, face impl, builder sugar
rxf/channels/      fuse (pyfuse3, extra), http (FastAPI, extra), ftp (pyftpdlib, extra)
include/rxf.h      GENERATED view of schema.py — banner-gated, the metal mod sync pattern
rxf.schema.json    GENERATED view of schema.py — ships in the wheel as a data file
```

**Why Python is the right outside, stated as a rule:** the tool stays small in any language
because the artifact carries the program model. At gen-0 the builder's essential complexity is
the *container* model — cells, sections, records — and the program rides in the artifact's own
self-description. A tool whose job is parse-emit-check of canonical blocks spends its language
freedom on portability and readability, and self-description is what makes the slowest language
affordable. The performance that matters later belongs to the *contained* core, which is the
porting ladder's first rung — so the first rung is useful work, not ceremony.

**Schema authority:** `schema.py` is the hand-written axiom set; the C header and the JSON
schema are generated views of it (banner write gate, regenerated by tooling, never
hand-edited) — the same shape as `metal mod sync`'s generated faces. The corpus schema check
compares schema.py's computed offsets against the generated header's `_Static_assert`s and
against actual bytes both spellings emit.

The CLI/REPL sugar is a **client of the face, not a wrapper of core internals** — otherwise the
programmatic path re-deroutes around the namespace. Sugar binds face ops only, with handles as
objects and typed refusals as exceptions.

Two distribution paths, two trust roles:

- `pip install rxf` — convenience, for users and agents. Someone else's build.
- `git clone && python -m rxf ...` — **certification**. "I built this myself from commit X."
  A fresh certification build consumes zero artifact-derived state and zero third-party
  dependencies: the repo and CPython are the entire trusted computing base. That smallness is
  the point — a compiled toolchain's dependency graph would make the measuring stick the
  biggest thing to audit; a stdlib-only build is auditable by one person.

Tool version never owns format version. The artifact header carries the format version; a tool
declares the range it reads and refuses outside it by name. PyPI is a transport, never an
authority.

## The porting ladder — fixed points, not vibes

The external tool mints the seed (gen-0). Capabilities port inward one at a time, each gated by
a byte-exact fixed point against the external tool's output — the same discipline as the rsx
self-host fixpoint already proven in-tree:

| Contained capability | Port proven when |
|---|---|
| reader/checker (71) | internal canonical dump == external dump, byte-exact |
| view generator (72) | internal view == external view, byte-exact |
| formatter (74) | internal successor of a trivial delta == external output, byte-exact |
| code emitter (γ of `05`) | internal emitted body == external emitted body, byte-exact |

**The flip criterion** is the formatter row: once the contained formatter produces the
system's own successors, development direction inverts — every change to the artifact is
authored as a view write -> delta -> successor, including changes to its own type records.

Do not share code between external and internal cores. Share the **byte schema** and the
**face** — and never trade input domains either. The external core consumes authoring
material (models, JSON, views) and writes seeds; the contained core consumes live state
through the face and writes successors. The external core never executes the artifact; the
contained core never reads an authoring file. The intrinsics are hand-written twice
(~50 lines each side — Python axioms in `schema.py`, C structs in the contained core), with
the corpus schema dump asserting the two spellings agree. Everything above the intrinsics is derived, in both places, from the same
meta-objects. The Python builder that minted gen-0 is frozen: regenerating from it must
reproduce the seed byte-for-byte, and from gen-1 on, meta-object changes go through the
artifact's own write path only.

The first contained seat is **unix** (mmap, the in-tree ELF relocator, no board bring-up in the
prove loop); firmware boards inherit the port after unix holds, with only the channel fills
differing. The port is a Python-to-C rewrite against the frozen face and schema — and because
the external side is Python, the C port's every fixed point is diffed against something a human
can read, which is the quorum's auditability made concrete at each rung.

## The quorum

The external build never retires. It is structurally required, not a safety habit:

| Role | When it is load-bearing |
|---|---|
| Bootstrapper | fresh host, no artifact yet — the seed must come from outside |
| Recovery path | a corrupt or unbootable artifact cannot rebuild itself |
| Quorum member | the trusting-trust answer (below) |
| Cross-target builder | the plasmid §10.2 shape: x86_64 builder, RISC-V/ARM artifact, target-side verification |
| External mount driver | permanent host residency, granted by claim (62) |

The plasmid filing's own words: *"Ein Fixpunkt darf nur ein Gate unter mehreren sein"* — a
fixed point is one gate among several, with reproducible-build quorums as the complement. A
self-hosting artifact that trusts only its own contained build is the trusting-trust shape
the filing refuses. The quorum is only real because the two builders are **genuinely
independent**: the contained C core is compiled into the artifact; the external core is
interpreted Python over a different runtime, a different memory model and a different
stdlib — maximally unalike implementations of one frozen schema. If the contained core were
generated from or shared code with the external one, two-agree would be vacuous — same bug,
same bytes. The Python side additionally stays the *readable oracle* at every rung of the
ladder: the thing the contained C is byte-diffed against is the version a human can audit
line by line.

Authority over the arc: the external tool **is** the authority at gen-0 (it mints the seed);
it becomes the **oracle** at the flip (fixed points diffed against it on every change); and in
steady state both are **quorum members** — an artifact's build is confirmed when the two agree,
and a disagreement is a loud event naming both, never a quiet preference for either.

## What stays hand-written, forever

The reader/checker core. If it is ever generated *by* an artifact, the two-implementations-agree
prove goes vacuous and the trusting-trust defense dissolves. The intrinsics stay the axioms.
Generated views (schema dump, C header mirror, stubs) are the house's `metal mod sync` shape —
banner-gated, checked in, regenerated from the canonical source — and the share of
record-driven tool content may grow over time, but the hand-written core shrinks toward a
floor of zero and never reaches it.

## Phase A milestones (replacing the stage-1..3 prefix of `09-PLAN.md`)

1. **Spine**: stdlib-only `rxf` core + face + CLI/REPL + builder sugar + corpus, all
   `direct`-channel. First prove: the seed as byte-frozen builder output — regenerate on the
   CI platforms and under different `PYTHONHASHSEED`s, digests match.
2. **Inspector**: FastAPI over the face (`rxf[http]`). Pretty immediately — it is where humans
   and agents live, and it is the embryo of the artifact's HTTP channel.
3. **FUSE**: the mount (`rxf[fuse]`); `diff -r` between two mounts becomes the successor
   review workflow.
4. **FTP**: the stress test (`rxf[ftp]`), last on purpose — the face must survive the
   crankiest client without special cases.

Stage 2 of the old plan (compiler refusal) already holds in-tree: the nomem escape is armed
around every compile path (`jit/c/__impl__.c`, `externals/tcc/libtcc.c:313`) and the
out-of-room prove (squeezed arena -> typed refusal -> healthy arena still compiles) exists in
`jit/c/__tests__.c`. The plan's remaining stages re-cut against the face/channels and the
porting ladder above; the container, boot, durability and successor stages consume the cell
allocator of `03` instead of a TLSF image.
